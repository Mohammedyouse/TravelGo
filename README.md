## 📖 Project Overview

**TravelGo** is a responsive, pixel-perfect travel and tourism booking frontend inspired by leading luxury hospitality platforms. Designed to bridge the gap between design fidelity and web engineering, it delivers a seamless booking journey across 16 interconnected screens without relying on heavy frameworks, compilers, or third-party runtime dependencies.

### Problems Solved
- **Complex Multistep Booking Experience**: Eliminates layout friction across hotel exploration, date/guest customization, suite comparison, guest verification, and payment checkout.
- **Client-Side SPA Responsiveness**: Delivers native mobile application performance inside modern web browsers with sub-50ms screen transitions, hash-based client routing, and responsive typography.
- **Zero-Setup Accessibility**: Evaluators, hiring managers, and prospective users can run the entire application directly in any browser with zero build steps, package installations, or backend setup.

## 🔒 Security, Privacy & Data Protection

Because this application serves as a portfolio demonstration and frontend prototype, security and privacy measures have been designed to protect user safety and demonstrate security-conscious engineering practices:

### 1. Secret-Free Architecture & Repository Sanitation
- **Zero Hardcoded Secrets**: The codebase contains **no** private API keys, backend database credentials, cloud access tokens, or sensitive internal endpoints.
- **Git Hygiene**: Strict `.gitignore` rules prevent accidental commits of `.env` files, build caches, design archives (`.fig`, `.zip`), and operating system metadata.
- **Private-by-Default Design**: The source code is organized so that sensitive integrations, production database keys, or payment gateways would live exclusively in an isolated server environment if attached to a live backend.

### 2. Client-Side Cryptographic Account Hashing
- When users register an account or demo credentials in the browser, passwords are **never** stored in plaintext.
- The state manager computes a salted SHA-256 hash using the native browser **Web Cryptography API** (`crypto.subtle.digest`), pairing each credential with an isolated cryptographic salt before saving to browser storage.

### 3. Safe Demonstration & Zero Financial Risk
- **No Real Transactions**: All payment card processing, voucher codes, and booking confirmation workflows are strictly client-side simulations.
- **No Card Data Transmission**: No real credit card information is ever transmitted to external servers, third-party payment gateways, or third-party tracking scripts.
- **Sandboxed Local Storage**: All session data, bookings, and reviews reside strictly within the user's local browser sandbox and can be wiped instantly using the "Reset Demo Data" control.

### 4. HTTP Security Headers
The production Netlify deployment configuration ([`netlify.toml`](netlify.toml)) enforces industry-standard protective HTTP response headers:
- `X-Frame-Options: DENY` (Mitigates clickjacking)
- `X-Content-Type-Options: nosniff` (Prevents MIME-type sniffing)
- `X-XSS-Protection: 1; mode=block` (Enforces legacy browser XSS filtering)
- `Referrer-Policy: strict-origin-when-cross-origin` (Safeguards referrer metadata)

## 💻 Running Locally

This project requires **no compilation, Node.js packages, or build toolchains**.

### Method 1: VS Code Live Server (Recommended)
1. Open this repository folder in **Visual Studio Code**.
2. Install the **Live Server** extension if not already installed.
3. Right-click [`index.html`](index.html) and select **Open with Live Server**.
4. The application will open automatically at `http://localhost:5500`.

### Method 2: Python Static Server
Run the following command from the project root directory:
```bash
python -m http.server 8080
```
Open `http://localhost:8080` in your web browser.

### Method 3: Node.js (npx)
```bash
npx serve .
```

### Version 1.1.0 — Frontend UI Fix — Welcome Screen and Responsive Layout
*Release Date: October 2026*

#### 🐛 Bug Diagnosis & Root Cause
- **Issue:** On the initial welcome screen, the lower ~254px portion of the phone viewport rendered as an empty, stark white rectangle beneath the Log In link.
- **Root Cause:** Flex height collapse on indefinite container height caused percentage-based child elements to collapse to auto content size (~590px instead of 844px), exposing the light viewport background.
- **Solution:** Configured full viewport flex architecture on `.app-viewport`, `.screen-container`, and `.screen-view` with `flex: 1; height: 100%`, locked background to `var(--color-deep-navy)` (`#0B1F3A`), and updated client router hooks for seamless zero-flash transitions.
